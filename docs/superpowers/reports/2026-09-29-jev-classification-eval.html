③ Threshold Policy

신뢰도 임계값별 폐기 정확도와 추출 넘김 비율

정책: 예측이 actionable이 아니고 confidence ≥ t일 때만 폐기하고, 나머지는 모두 추출로 넘긴다. confidence는 Jev가 확률 분포에서 계산한 값이다(Choice n개일 때 (n·p_max − 1)/(n − 1), 문서의 Confidence 페이지). 행동 항목 유실(actionable을 폐기)이 가장 비싼 오류라서 이를 기준으로 고른다.

2회차 기준. 1회차에서는 p08 confidence가 0.88이라 t=0.9일 때 누수 2건이었다. 서버 규칙을 먼저 적용해도 표는 같다. 규칙이 버린 6건은 Jev도 모두 버렸기 때문이다.

제안: t = 0.8. 세 번의 실행(rubric 2회·bare 1회) 모두 actionable 유실이 0건인 가장 낮은 임계값이다. t=0.6 이하에서는 bare 설정이 a08(0.65)을 버린다. 대가는 저신뢰 비행동 항목이 추출로 새는 것(이번에 60건 중 1건)이다. 새어도 6단계 추출 분류의 discard가 한 번 더 거른다. 0.9는 얻는 것 없이 누수만 늘어난다. 버전이 바뀌면 confidence 분포도 바뀌므로 모델은 jev-latest 대신 jev-1.13.0으로 고정한다(문서 권고).

⑥ Conclusion

게이트로 채택할지, 언제 OpenAI 소형 모델로 바꿀지

판단: 조건부 채택. 합성 60건에서 게이트 정확도 100%(목표 90%), 행동 항목 유실 0, p95 약 0.27초, 월 수 센트다. 실기기 FM이 놓친 잡담 2건을 확신도 1.00으로 걸렀고, 규칙이 놓친 OTP 2건도 잡았다. 다만 아래 조건을 먼저 채워야 한다.

채택 전제 (모두 충족 시)

  • 벤더 결정: 스펙 §2 “AI 벤더 OpenAI 단일” 결정과 충돌한다. 게이트를 붙이면 복호화한 본문이 두 번째 외부 공급자로 나간다. 사용자 결정과 스펙 §2·§12 통제 3 개정이 필요하다.
  • 데이터 보관: TypeSafe DPA에는 “필요한 기간 동안 보관”만 있고 기간이 없다. ZDR은 엔터프라이즈 전용이다. OpenAI(store:false, 남용 모니터링 최대 30일)와 같은 수준인지 확인해야 한다(⑦-1·2).
  • 실데이터 재측정: 실제 분포(카톡 알림톡, 약속이 섞인 지인 대화, 날짜 있는 기관 안내)에서 200건 이상을 재측정한다. 원문을 남기지 않고 라벨·confidence만 기록한다. 통과 기준은 게이트 정확도 ≥ 90%이고, t=0.8에서 actionable 유실 ≤ 1%다.
  • 운영 설정: jev-1.13.0 고정, t=0.8, fail-open(오류 시 추출로), 폐기 사유 코드 discarded:jev:<label> 감사 로그.

OpenAI 소형 모델(gpt-6-luna 분류)로 바꾸는 조건 (하나라도 해당 시)

  • 벤더 추가가 승인되지 않거나, TypeSafe 보관 조건이 OpenAI store:false보다 약하다.
  • 실데이터에서 게이트 정확도가 90% 미만이거나, t=0.8에서 actionable 유실이 1%를 넘는다(문서상 한국어는 주 언어가 아니다).
  • worker 운영 중 429/529로 fail-open 비율이 5%를 넘는다(한도가 동적이라는 경고가 있다).
  • Edge 리전에서 p95가 1초를 넘어 cron 1분 주기의 처리량을 잡아먹는다.

gpt-6-luna로 바꿔도 비용 차이는 월 약 $0.1이고, 분류 요청을 추출과 같은 공급자·약관 안에 둘 수 있다. 하지만 confidence가 보정된 확률로 나오지 않아 ③의 임계값 정책을 그대로 옮길 수 없다. 이 경우 “discard 라벨만 폐기, 나머지는 추출” 규칙으로 단순화한다.
